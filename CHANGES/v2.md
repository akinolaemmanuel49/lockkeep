# v2 — Workspace-Aware Release with Shared Secrets

The workspace milestone: organizations (workspaces), teams, and shared secrets
with end-to-end-graded encryption. The personal vault stays a distinct,
user-owned feature; workspace secrets live under their own hierarchy.

## Added

- **Workspaces (organizations).** Create, edit, delete, and inspect workspaces;
  per-workspace teams and membership.
- **Workspace shared secrets**, scoped **organization → application →
  environment**:
  - Applications and environments with slug-based routing; environments are
    optionally marked *protected*.
  - Secrets keyed by name with kinds `env | note | file | json`, versioned on
    every update, and deleted on request.
  - Human facing UI in the workspace detail page (view, add, update, reveal,
    and delete secrets).
  - **Bulk secret entry (UI-only).** Replicate the secret *keys* of one
    environment to another without copying values (each environment stays
    unique), and import a `.env` file to prefill a reviewable batch editor
    before saving.
- **CI demo app** (`lockkeep-example/`). A `run` wrapper that fetches an env
    in a single API call and injects the secrets as `process.env` variables
    before spawning the app — service code reads plain env vars. Includes a
    GitHub Actions workflow (`.github/workflows/ci-secrets.yml`) that does the
    same on hosted runners from repository secrets.
- **Envelope encryption for shared secrets.** Each environment gets its own
  32-byte data key (DEK) wrapped by a server KEK behind a `KeyProvider`
  abstraction (local provider today; a cloud-KMS implementation can be swapped
  in without touching services). Secret values are sealed with AES-256-GCM and
  authenticated using `environmentId|key|version`.
- **Re-wrap on read.** When a human lists a workspace's secrets, the API unwraps
  the DEK server-side and returns plaintext so the UI can behave like a normal
  secret manager.
- **Machine access.** Service accounts can mint per-environment API keys
  (`lk_live_…`); `GET /api/v2/machine/secrets` authenticates with the key alone
  and returns an **export envelope** containing only ciphertext plus a
  wrapped DEK. Clients derive a wrapping key from their API key via
  HKDF-SHA256, unwrap the DEK, and decrypt — plaintext never crosses the
  machine endpoint.
- **Machine access console UI.** On each application's page, manage service
  accounts, mint environment-scoped read-only keys (with optional
  expiration), revoke them, and verify the key in-browser by fetching and
  decrypting the envelope — proving the exact flow CI will use.
- **`@lockkeep/sdk`.** Zero-dependency TypeScript client for Node ≥ 18 and
  browsers: `fetchSecrets` / `fetchEnvVars` implement envelope fetch,
  HKDF unwrap, and AES-GCM decrypt so servers and pipelines can read
  environment variables from a plain `lk_live_…` key.
- **RBAC.** Permission-gated routes (`RequirePermission`) with
  membership-first checks, plus audit events for security-relevant actions.
- **Vault parity.** All six vault record types and seamless unlock-on-save for
  the personal vault.
- **Change notes.** This directory.

## Changed

- Route layout split: personal vault under `/me/vault/*`, workspace resources
  under `/organizations/*`, machine access under `/machine/*` — no overlap.
- Full UI rework (dashboard, vault, workspaces, settings, setup, crypto-policy
  admin) in the new v2 shell.
- Committed submodules were vendored into the monorepo.

## Environment Variables

- `LOCKKEEP_KEK` — 32-byte hex key-encryption key guarding environment data
  keys. Generate once, keep stable across restarts (rotating it requires
  re-wrapping every environment DEK).
- `LOCKKEEP_API_KEY_HASH_SECRET` — 32-byte hex secret used to hash API keys
  (`lk_live_…`) at rest so machine credentials are never stored in the clear.

## Notes

- Machine endpoint returns `kdf.salt` and `wrappedDek.aad` as the environment ID
  hex **string**; clients must UTF-8-encode (not hex-decode) those fields.
- Invitations, role assignment, and the management UI for both are a later
  phase.
